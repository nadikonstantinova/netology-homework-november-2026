Защита сети — Константинова Надежда

Проверка выполнена в изолированной учебной подсети 10.113.77.0/24. Защищаемая система — 10.113.77.20, система сканирования — 10.113.77.10. Установлены Suricata 7.0.10, Fail2Ban 1.1.0, Nmap 7.95 и Hydra 9.5. На защищаемом узле работает SSH.

Задание 1. Разведка системы и анализ событий

Выполнены четыре режима проверки. Для воспроизводимости выбран диапазон TCP-портов 1–100:

nmap -sA -Pn --reason -p 1-100 10.113.77.20
nmap -sT -Pn --reason -p 1-100 10.113.77.20
nmap -sS -Pn --reason -p 1-100 10.113.77.20
nmap -sV -Pn --reason -p 1-100 10.113.77.20

Результаты:

Режим Наблюдение
-sA, ACK Все 100 проверенных портов имеют состояние unfiltered, ответ — TCP RST. Этот режим проверяет фильтрацию, а не определяет открытые порты.
-sT, connect Порт 22/tcp открыт, остальные 99 портов закрыты. Выполняется TCP-соединение.
-sS, SYN Порт 22/tcp отвечает SYN/ACK, закрытые порты — RST. Полное прикладное соединение для SYN-проверки не требуется.
-sV, определение версии На 22/tcp распознан OpenSSH 10.0p2 Debian 7+deb13u4, протокол SSH 2.0.

Выводы команд: ACK, connect, SYN, определение версии.

События Suricata

Загружены приложенные учебные правила: пороговая фиксация SYN- и ACK-пакетов, а также повторных SSH-пакетов. Примеры реально записанных событий:

11/13/2026-20:22:36.346795 [1:1000002:1] LAB TCP ACK scan threshold
10.113.77.10:50454 -> 10.113.77.20:34

11/13/2026-20:22:36.765392 [1:1000001:1] LAB TCP SYN scan threshold
10.113.77.10:38244 -> 10.113.77.20:36

11/13/2026-20:22:38.061992 [1:1000003:1] LAB repeated SSH connection attempts
10.113.77.10:57886 -> 10.113.77.20:22

Suricata увидела поток проверки множества портов и SSH-трафик при определении версии службы. Эти правила демонстрируют работу IDS, но не являются полноценным набором производственных сигнатур: обычные ACK-пакеты тоже могут достигнуть заданного порога. Срабатывание учебного SSH-правила означает повторные пакеты распознанного SSH-протокола, а не обязательно несколько независимых подключений или подтверждённый подбор пароля.

Полный журнал этапа: Suricata fast.log.

События Fail2Ban

После сканирования в jail sshd получено:

Total failed: 0
Currently banned: 0
Total banned: 0

Это ожидаемый результат: SYN/ACK-сканирование и чтение баннера SSH сами по себе не создают неудачных попыток парольной аутентификации. Fail2Ban анализирует журнал SSH, поэтому не должен автоматически блокировать адрес только из-за таких пакетов. В его журнале на этом этапе находятся события запуска jail, но нет Found и Ban.

Задание 2. Проверка подбора пароля SSH и блокировки

Подготовлены файлы users.txt с двумя учебными именами и pass.txt с пятью заведомо неверными паролями. Всего задано десять сочетаний; действующие пароли пользователей в словари не добавлялись.

Для современного Fail2Ban включён jail sshd через отдельный конфигурационный файл jail.d/netology.local:

[DEFAULT]
bantime = 300
findtime = 120
maxretry = 3
ignoreip = 127.0.0.1/8 ::1
banaction = iptables-multiport

[sshd]
enabled = true
backend = polling
port = ssh
filter = sshd
logpath = /var/log/auth.log

Выполнена ограниченная проверка против учебного узла:

hydra -L users.txt -P pass.txt -t 2 -W 1 -w 3 -I -V 10.113.77.20 ssh

Журналы SSH и Fail2Ban

В auth.log появились Failed password, а в Fail2Ban — события обнаружения и блокировки:

2026-11-13 20:22:46,717 [sshd] Found 10.113.77.10
2026-11-13 20:22:48,718 [sshd] Found 10.113.77.10
2026-11-13 20:22:48,907 [sshd] Ban 10.113.77.10

После проверки статус jail подтвердил:

Total failed: 5
Currently banned: 1
Total banned: 1
Banned IP list: 10.113.77.10

При maxretry = 3 общее число зарегистрированных ошибок может быть больше трёх: несколько попыток уже выполнялись параллельно в момент установки блокировки.

В цепочке f2b-sshd появилось правило REJECT для 10.113.77.10. На момент сохранения результата его счётчик содержал 37 пакетов. Это подтверждает не только запись о бане в журнале, но и фактическую обработку последующего трафика правилом межсетевого экрана.

События Suricata во время SSH-проверки

В интервале проверки появились 18 событий учебного SSH-правила, два события порогового ACK-правила и одно SYN-событие. Suricata видит сетевое поведение и распознаёт SSH, но содержимое парольного обмена зашифровано. Достоверный признак неудачной аутентификации здесь даёт auth.log, а блокировку подтверждают Fail2Ban и правило iptables.
